## 4. 第一期复现目标

先完成单模型、单基准、三种方法的可核验复现：

- 原始模型：`Qwen/Qwen3-4B`，代码标识为 `qwen-4b`；固定模型与tokenizer版本。
- 方法：Vanilla、DEER、CoDE-Stop。
- 正式基准：MATH500，共500题，每题2次生成，即1000条基础轨迹。
- 正式最大新生成token数：32768；这是输出上限，不是输入加输出的总上下文长度。
- 三方法共享基础推理记录；Vanilla包含接近预算上限时的强制收尾。
- 每种方法最终都需覆盖同一组1000个唯一的题目/rollout组合，并保留异常与判分情况。
- 先采用可核对的已发表参数，不默认重做AMC23校准。DEER主表参数对应关系等不明确部分需先核对；不能猜作作者原设置。
- BF16、提示、采样、种子规则、判分、方法参数和所有版本在正式运行前冻结。

这些模型/采样/共享轨迹设置依据[论文§3.1](https://arxiv.org/html/2604.04930v2#S3.SS1)。固定参数重跑与AMC23重新校准是两种任务；不应把前者称为完成了校准流程。

前期可以用教学样例、独立开发题和短输出做诊断，需单独标记，不能混入正式32K结果。开发/校准/测试按题分开，同题不同rollout不能跨集合。测试结果不能用于反复挑阈值或新规则。

第一期交付：可执行命令和必要代码、环境/版本/配置清单、配对且完整的结果、准确率和token统计、实际耗时与显存、异常核验、备份，以及复现报告。验收基于流程和证据完整，不要求逐点达到原文数字。

当前代码与论文算法存在差异。若采用上游实现，报告限定为固定上游实现的复现；完成公式和配置对齐后再使用相应表述。暂不同时扩展全部模型、全部对照、训练/RL和在线部署，也不将复现本身承诺为投稿创新。

## 5. 必须先理解的代码关系

```text
inference.py：读取参数、加载模型/数据、调方法、判分、保存
    ├── models.py：加载模型和tokenizer；普通生成
    ├── dataset_loader.py：得到题目和标准答案
    ├── method_prompts.py：step-by-step基础生成
    ├── generic_forceans()：必要时为基础回答强制收尾
    ├── method_deer.py / method_codestop.py：探测前缀并决定停止
    └── llm_eval.py：答案提取和判分

JSONL结果 → 完整性核验 → basic_results.py：汇总指标
```

实际方法依赖：

```text
step-by-step → step-by-step-forceans → deer / codestop
```

每个阶段单独执行，程序不会自动补跑前置步骤。缺依赖记录可能报错或跳题。

当前上游实现先生成完整基础轨迹，再在其前缀上执行试答和停止判断；试答/最终补答仍需运行模型。由此得到的token工作量不能直接视为实测在线加速或租金节省。

几个重要区别：

- 模型输出的试答置信度用于停止判断，答案正确性由评测程序判断。
- 磁盘JSONL缓存与模型KV cache不是一回事。
- `N`表示每题生成次数，不是训练轮数；分块参数表示题目划分，不是GPU张数。
- `response_tokens`是方法返回的文本长度统计；`work`包含部分试答等开销。最终报告必须核对计数边界，另测实际时间。
- `basic_results.py`按记录行汇总；同题有多次rollout。它与 `compact.py` 都不替用户去重，合并文件不是运行必需步骤。

| 问题 | 接手后的处理 |

| 环境配置仍为占位内容；输出目录默认值存在风险 | 准备本地私有配置，显式指定输出目录；不将密钥写进Git |

| MATH500使用LLM判分，默认 `gpt-4o-mini` | 先确认裁判服务可用；换成本地判分属于协议变化，须明确并检查分歧 |
| CoDE默认 `use_log=True`，且只累计置信度下降的相邻段 | 与论文v2概率公式逐项对照；保留算法版本差异，不静默修改 |
| 极短试答的置信度计算有数值边界问题 | 手算及少量真实输出检查，明确非有限数处理，不把异常置信度计为正常 |

| 缓存身份未覆盖完整版本/seed；缺样本可能跳过 | 输出目录隔离，增加版本和唯一键核验，明确每题每rollout的种子规则 |
| 汇总可能跳过坏行、也不去重 | 核对预期/实际/唯一记录数及方法间配对，禁止静默丢弃失败项 |
| 短题跑通不能说明32K可运行 | 测短、中、长前缀及试答峰值，保留时间和显存记录 |

## 9. 接手后立即做什么
