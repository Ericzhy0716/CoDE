## 4. 第一期复现目标

先完成单模型、单基准、三种方法的可核验复现：

- 原始模型：`Qwen/Qwen3-4B`，代码标识为 `qwen-4b`；固定模型与tokenizer版本。
- 方法：Vanilla、DEER、CoDE-Stop。
- 正式基准：MATH500，共500题，每题2次生成，即1000条基础轨迹。
- 正式最大新生成token数：32768；这是输出上限，不是输入加输出的总上下文长度。
- 三方法共享基础推理记录；Vanilla包含接近预算上限时的强制收尾。
- 每种方法最终都需覆盖同一组1000个唯一的题目/rollout组合，并保留异常与判分情况。
- 先采用可核对的已发表参数，不默认重做AMC23校准。DEER主表参数对应关系等不明确部分需先核对；不能猜作作者原设置。
- BF16、提示、采样、种子规则、判分、方法参数和所有版本在正式运行前冻结。

这些模型/采样/共享轨迹设置依据[论文§3.1](https://arxiv.org/html/2604.04930v2#S3.SS1)。固定参数重跑与AMC23重新校准是两种任务；不应把前者称为完成了校准流程。

前期可以用教学样例、独立开发题和短输出做诊断，需单独标记，不能混入正式32K结果。开发/校准/测试按题分开，同题不同rollout不能跨集合。测试结果不能用于反复挑阈值或新规则。

第一期交付：可执行命令和必要代码、环境/版本/配置清单、配对且完整的结果、准确率和token统计、实际耗时与显存、异常核验、备份，以及复现报告。验收基于流程和证据完整，不要求逐点达到原文数字。

当前代码与论文算法存在差异。若采用上游实现，报告限定为固定上游实现的复现；完成公式和配置对齐后再使用相应表述。暂不同时扩展全部模型、全部对照、训练/RL和在线部署，也不将复现本身承诺为投稿创新。

## 5. 必须先理解的代码关系

```text
inference.py：读取参数、加载模型/数据、调方法、判分、保存
    ├── models.py：加载模型和tokenizer；普通生成
    ├── dataset_loader.py：得到题目和标准答案
    ├── method_prompts.py：step-by-step基础生成
    ├── generic_forceans()：必要时为基础回答强制收尾
    ├── method_deer.py / method_codestop.py：探测前缀并决定停止
    └── llm_eval.py：答案提取和判分

JSONL结果 → 完整性核验 → basic_results.py：汇总指标
```

实际方法依赖：

```text
step-by-step → step-by-step-forceans → deer / codestop
```

每个阶段单独执行，程序不会自动补跑前置步骤。缺依赖记录可能报错或跳题。

当前上游实现先生成完整基础轨迹，再在其前缀上执行试答和停止判断；试答/最终补答仍需运行模型。由此得到的token工作量不能直接视为实测在线加速或租金节省。

几个重要区别：

- 模型输出的试答置信度用于停止判断，答案正确性由评测程序判断。
- 磁盘JSONL缓存与模型KV cache不是一回事。
- `N`表示每题生成次数，不是训练轮数；分块参数表示题目划分，不是GPU张数。
- `response_tokens`是方法返回的文本长度统计；`work`包含部分试答等开销。最终报告必须核对计数边界，另测实际时间。
- `basic_results.py`按记录行汇总；同题有多次rollout。它与 `compact.py` 都不替用户去重，合并文件不是运行必需步骤。

8. 每日答复包含：已核验完成项、当前阻塞、下一天任务与时间分配、后续顺延影响。
9. 用户汇报后再更新状态；当前没有设置自动检查、提醒或后台实验。

Notion接入前，有工作区权限时更新 `docs/REPRODUCTION_PROGRESS.md` 的阶段、证据、剩余项和调整记录；没有文件权限时，在对话中给出待保存的进度摘要。Notion接入并回读核验后，日常任务状态按第9节以Notion为准，Markdown进度文件保存快照。正式阶段目标或验收标准有变化时，更新 `docs/REPRODUCTION_PLAN.md` 并在Notion说明原因。任何时候都不声称完成了未经工具核验的写入。

## 9. Notion接入与日常任务管理方案

### 9.1 先核对实际状态

以下是拟定方案，不表示页面和数据库已经存在。用户开始接入时，主对话先确认当前环境是否已有可用Notion连接、目标工作区/页面，以及对目标数据库的实际读写能力。若已连接，复用当前连接；若尚未连接，再协助安装和授权。[插件安装与服务连接说明](https://learn.chatgpt.com/docs/plugins)

连接成功、能看到页面、创建任务成功是不同状态。记录目标页面/数据库的实际链接，读回写入内容后才报告接入或迁移完成。当前对话无法访问的Notion页面、权限和内容均标为待核验，不推测另一个账号的连接已自动继承。

用户当前请求仅是更新交接文档。没有执行Notion写入，也没有设置后台自动同步、定时提醒或监控。

### 9.2 先建立一个简单工作台

建议工作台名称：**CoDE-Stop复现工作台**。先使用一个任务数据库：**复现任务**。

首页放四项内容：本期目标、当前阶段、十阶段大纲、当前需要解决的阻塞。数据库中每行是一项可验收的任务，如“理解普通生成调用链”，而非笼统的“今天做实验”。先拆最近1–2天的具体任务，后续阶段保留在大纲中，临近时再细化。

以下字段为初始设计，可按实际工具能力调整：

| 字段 | 建议形式 | 记录规则 |
| --- | --- | --- |
| 任务名称 | 标题 | 说明要完成的具体动作 |
| 任务编号 | 文本 | 如 `D1-01`；创建后保持不变，不因顺延或改名变化 |
| 所属阶段 | 选择 | D1至D10，对应本文件阶段表 |
| 状态 | 状态或选择 | 未开始、进行中、受阻、待核验、完成 |
| 原计划日期 | 日期 | 首次确定的日期，顺延时保留；尚未确定则留空 |
| 当前计划日期 | 日期 | 目前安排执行的日期，顺延时更新 |
| 预计用时（小时） | 数值 | 初始估算；剩余工时另记，避免覆盖原估算 |
| 累计实际用时（小时） | 数值 | 根据用户汇报累加，不根据聊天时长猜测 |
| 实际完成日期 | 日期 | 达到验收标准后填写 |
| 完成标准 | 页面正文或文本 | 预先说明怎样算完成 |
| 完成证据 | 页面正文、文本或链接 | 可核验的输出、文件、截图说明、解释记录或结果摘要；本地路径不等于远端对话可访问 |
| 阻塞/剩余工作 | 页面正文或文本 | 问题、已尝试措施、剩余步骤及预计剩余工时 |

任务页面附一个简短调整记录，保存：调整时间、原因、原日期→新日期、剩余工作、影响的后续阶段。保留历史，不把顺延后的日期伪装成原计划。

### 9.3 建议视图

- **今日与延期**：当前计划日期为今天或更早、状态尚未完成的任务；按受阻/待核验/进行中等情况查看。
- **受阻与待核验**：集中显示需要排错或补充证据的项目。
- **全部阶段**：按D1至D10分组，了解每一阶段的任务情况。

总进度以“已验收阶段数/10”和当前剩余工作说明为主。当天三个子任务完成，不代表整个研究已完成；不要按聊天条数或随意拆分的任务数量计算课题完成度。

### 9.4 D1可直接采用的任务内容

以下仅是待录入模板；日期待用户实际开始时确定，状态均为未开始。

| 编号 | 任务 | 预计用时 | 完成标准 |
| --- | --- | --- | --- |
| D1-01 | 理解普通生成调用链 | 2小时 | 能解释 `sample['question'] → messages → input_ids → outputs → response` |
| D1-02 | 理解论文目标和程序入口 | 1.5小时 | 能说明三种方法、主要指标和程序调用关系，记录阅读疑问 |
| D1-03 | 整理本地准备与首日报告 | 2.5小时 | 确认已有目录/工具状态、数据用途和部署信息，保存笔记及未解决问题 |

这三项合计6小时，另留0–2小时缓冲。任务预计时间用于分配精力，不是强制用满。

### 9.5 每天怎样更新

1. 开始时读取最新任务和上一日报告，结合用户新汇报，确定当天最多三个主要目标。
2. 核对已有任务编号，优先更新原记录；同一任务顺延时不创建一个新的同名任务。
3. 用户汇报后，先核验完成标准与证据，再更新状态、实际用时和剩余工作。仅“程序跑完”时可先标为待核验；明确卡在外部条件或错误时标为受阻。
4. 部分完成时保留产物和累计实际用时，记录剩余工时；只把剩余工作安排到后续日期，不要求重做已通过部分。
5. 顺延时保留原计划日期，更新当前计划日期，追加原因和影响。只移动依赖它的后续任务；不相关的本地阅读可以继续。
6. 写入后读回任务，核对状态、日期、工时和备注。向用户报告实际成功更新的内容；失败或未核验的更新明确列出。

例如：D2-02模型下载尚未完成，次日继续同一个D2-02，保留已下载文件和已投入时间，追加剩余分片检查；依赖模型的首次生成随之顺延。不要把原任务标成完成后另建“继续下载”来抬高完成数量。

### 9.6 Notion与Markdown如何保持一致

| 阶段 | 日常进度以哪里为准 | Markdown的作用 |
| --- | --- | --- |
| 当前，尚未接入 | `REPRODUCTION_PROGRESS.md` | 保存最新阶段、证据、阻塞与下一步 |
| 接入/迁移中 | 仍以已核验的Markdown记录为准 | 作为迁移来源；迁移成功前不切换 |
| 迁移并回读验收后 | 指定Notion任务数据库 | 保存带导出时间的进度快照，供交接和备份 |

切换时记录：生效日期、主对话、目标Notion链接、已迁移的任务编号及读回核验结果。在阶段结束或更换对话前导出一次进度快照；有重要变动时可按需追加。不要让两个账号同时把不同内容覆盖成“最新进度”。

正式方案、配置和研究结论仍保存在项目仓库。Notion记录任务状态、结论摘要和证据位置；模型权重、大量原始输出、密钥和SSH认证信息不搬进任务表。

若Notion暂时不可用，保留最近快照，在当前对话或Markdown记录一份“待同步变更”，标明任务编号、依据和时间。不要宣称已同步；恢复后先读取远端最新状态，再合并这批变更，避免用旧快照覆盖新记录。

接手助手获得用户新的日常汇报后再推进更新。定时提醒、自动轮询、无人值守写入和新的预算支出均不是本文件已实施的功能。

## 10. 接手后立即做什么

当前从D1开始，先确认用户自交接后是否已有新进展。若没有，直接带用户打开 `upstream/CoDE-Stop/method_prompts.py` 的 `method_step_by_step()`，然后进入 `models.py` 的 `generate()`。

第一轮只围绕这些问题展开：

1. `sample['question']` 如何组成 `messages`？
2. 聊天模板和tokenizer如何把文字变成模型输入？
3. `model.generate()` 接收什么，`B`控制什么？
4. 输出如何还原成回答，返回了哪些字段？

D1建议分配：确认目录0.5小时、论文略读1小时、上述代码精读2小时、工具与数据用途准备1.5小时、画调用链及整理问题1小时。结束时根据实际完成情况更新进度，不预先认定当天必能完成。

Notion接入可以与本地学习准备并行。先完成连接状态和目标页面核对；尚未接入时，继续更新Markdown，不让工具配置阻塞D1学习。收到用户实际接入要求后，按第9节先建立最小任务表并读回核验，再切换进度主记录。
