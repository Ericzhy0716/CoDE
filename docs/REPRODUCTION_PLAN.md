## 一、第一期目标与完成标准

先用10个有效工作日学习并完成一套可复现的单模型实验流程，另预留2–4个弹性工作日。每天按6小时核心任务安排，余下0–2小时用于排错或巩固。正式批量实验需要多少GPU小时尚未实测；D8–D9是初始排期窗口，不能保证在两天内完成。

第一期范围：原始 `Qwen/Qwen3-4B`，Vanilla、DEER、CoDE-Stop三种方法，目标测试集为MATH500。先做单题与独立开发样本诊断，通过后再完成500题、每题2次、最大新生成32768 token的子集。三方法共享基础推理记录；Vanilla需要包含接近预算上限时的强制收尾处理。这些目标设置依据[论文v2 §3.1](https://arxiv.org/html/2604.04930v2#S3.SS1)。

这次先采用可核对的已发表参数，不默认重做AMC23校准。模型、数据、提示、精度、采样、判分和具体停止参数在D7冻结。DEER参数的主表对应关系仍需核对；未公开部分标明来源和不确定性，不猜作原始配置。若后续要自行调参，再启用独立校准协议。

第一期结束应交付：

1. 能从准备环境到生成、探测、判分、统计独立完成一次运行，并解释关键输入输出。
2. 可重复执行的命令、配置、版本清单及必要工程修补，原作者固定副本保持不变。
3. 三方法各1000条唯一且相互配对的测试记录，以及基础生成中间记录；失败、漏题、重复和未判分项目必须有明确统计，不能静默丢弃。
4. 准确率、输出token、含探测的token工作量、实际耗时和显存记录；逐项注明计数口径。
5. 一份报告说明已覆盖范围、论文/代码差异、结果偏差和未完成项。没有达到论文同样的数值也可以形成完整、诚实的复现报告。

当前公开代码与论文公式有差异。工程修补和算法改动分别记录；若本轮采用上游算法，就报告“固定上游实现的指定子集复现”。只有完成相关公式和配置核对后，才称为论文方法对齐复现。无需在第一期同时运行两套完整矩阵。

第一期暂不扩展14B模型、全部基准、全部对照、训练/RL、在线服务改写或新方法论文。后续扩展依据本期结果单独安排。

## 三、先认识这些词

| 术语 | 在本项目中的意思 |
| --- | --- |
| inference / 推理 | 使用已训练模型生成答案，本期不训练模型 |
| token / tokenizer | 模型处理的文本单位，以及文字与这些单位之间的转换工具；token数不是字数 |
| prompt | 实际传给模型的题目和指令，包含聊天模板 |
| rollout / trajectory | 某道题的一次完整生成；同一道题可以采样多次 |
| baseline / 对照 | 用于比较的方法，例如普通生成Vanilla |
| checkpoint / 检查点 | 本方法尝试停止推理的位置；此处与“模型权重检查点”含义不同 |
| KV cache | 复用前缀计算的内存/显存缓存，与磁盘JSONL结果缓存不同 |
| seed / 随机种子 | 控制随机采样的一项设置；不能保证跨设备或版本逐token相同 |
| JSONL | 每行保存一条独立JSON记录，便于逐条保存和续跑 |
| smoke / 运行诊断 | 少量输入检查流程；不能据此评价论文效果 |
| development / calibration / test | 开发排错、选择参数、最终评估三种用途，按题划分 |

## 四、十个任务日

### D1：看懂最小流程，做好本地准备

**位置：Mac；无需GPU。目标：能解释一道题怎样变成一条回答。**

- 0.5小时：确认现有目录和上游版本。项目已建立，不重复创建、重新下载整个项目或重做目录工作。
- 1小时：略读论文摘要、图1和§3.1；记录论文解决的问题、输入输出、三种比较方法、主要指标。方法公式今天先看含义。
- 2小时：精读 `method_prompts.py` 的 `method_step_by_step()` 和 `models.py` 的 `generate()`；在VS Code中跟踪 `sample['question'] → messages → input_ids → outputs → response`。略读 `inference.py` 的主循环和方法依赖表。
- 1.5小时：认识Python环境、依赖与Git子模块；检查本地Python/Git和项目版本，列出服务器配置项。划清教学、开发、校准和最终测试的用途，确定开发数据来源及去重规则；真正的开发样本在使用前与AMC23/MATH500按题去重。Mac先用于阅读、轻量处理和记录，不安装完整CUDA环境。
- 1小时：用自己的话记录关键调用链、当天三个疑问及次日部署清单；助手协助整理。

**产物：** 一张简单调用链/文字笔记；部署所需信息和数据用途清单。学习笔记可先放在忽略提交的 `runs/learning/`，整理后再分享必要内容。

**通过条件：** 能指出问题文本、模型生成入口、token上限、返回回答和保存入口。无需今天掌握Transformer内部推导。

### D2：部署环境，得到第一条模型输出

**位置：Mac准备，服务器运行。目标：验证环境与模型可以实际工作。**

- 1小时：确定本轮GPU及可用内存/磁盘、费用上限、停止时间；确认代码同步状态，再获取固定上游副本。首次生成前明确日志及原始输出保存方式，先保存生成、再执行判分；必要的最小封装由助手讲解后再由用户执行。第一期只准备4B权重。
- 2小时：创建独立Python环境，安装经过核对的依赖；检查实际GPU可用性、CUDA构建与BF16计算。驱动显示CUDA版本不等于PyTorch已能使用GPU。
- 1.5小时：下载并检查模型、tokenizer与数据文件，固定来源和revision。不能仅凭 `config.json` 存在就认定全部权重下载完成。
- 1小时：在一个教学样例上生成短输出，记录命令、输出、用时及显存。缩短token上限时明确标为诊断，不进入正式结果。
- 0.5小时：保存环境和日志，核验备份位置。

**产物：** 环境记录、模型文件完整性检查、第一条实际输出。

**通过条件：** 用户能独立再次运行该样例；实际调用到GPU；输出和日志有保存位置。下载/安装未完成就继续D2，不赶到D3。

### D3：把生成、补答、判分和保存串起来

**位置：Mac阅读/检查，服务器做少量生成。目标：拿到可追溯的单题结果。**

- 1.5小时：精读 `generic_forceans()`、结果写入部分和MATH500对应判分函数，区分原始回答、强制收尾、抽取答案和裁判结果。
- 1小时：准备判分服务并做一次小型可用性检查。密钥使用本地/服务器私有配置，不进入聊天或Git。若更换判分方式，单列协议差异。
- 2小时：在预先选定的1–3个开发样例上按依赖顺序运行基础生成与forceans，保留各阶段输出。
- 1小时：验证D2准备的“先保存生成、再可靠判分”路径，在已保存结果上检查一次判分失败后的重试，确认不重复生成或计入结果。原作者程序判分先于保存，不能把未经处理的入口直接用于昂贵批量任务。
- 0.5小时：亲自读一条JSONL，核对题目、标准答案、回答、token和判分字段。

**产物：** 可追溯的样例记录；明确的输出路径；判分成功/失败的记录方式。

**通过条件：** 生成、判分与落盘都已验证；重新读取能找到相同样例。判分未完成必须保持“待判分”状态。

### D4：理解并运行DEER

**位置：本地理解，服务器试答。目标：理解“为什么能在中途要求模型回答”。**

- 1.5小时：精读 `method_deer()` 和试答置信度函数，理解推理前缀、检查点、试答提示和阈值。
- 1小时：解释KV cache与磁盘结果缓存的区别，确认当前 `cp_cache` 设置。
- 2小时：先只观察一个检查点的试答，再运行同一条开发轨迹的DEER；记录试答、token概率、置信度、停止位置及最终回答。
- 1小时：核查极短试答的数值边界；零/一个有效token、非有限数等要有明确处理记录，不能把NaN当作有效置信度。
- 0.5小时：复盘这条题目中的停止理由。若没触发停止，也记录原因，不通过临时降阈值制造“成功”。教学时演示其他阈值需单独标记。

**产物：** 一条检查过程可解释的DEER记录及数值诊断。

**通过条件：** 能从记录说明检查位置、试答置信度和停止判断；有答案输出；无未解释的非有限值。题目是否答对不是本日的通过标准。

### D5：理解CoDE-Stop，确认论文与实现差异

**位置：Mac为主，少量GPU。目标：知道CoDE比DEER增加了什么。**

- 1.5小时：精读论文§2.2，画出“置信度分支”和“退化分数分支”。
- 1.5小时：精读 `compute_ramping_deer_threshold()`、`compute_degeneration_score()` 和 `method_codestop()`；用一段明确标为教学用的置信度序列手算阈值、分数和停止点，与代码逐项核对。
- 1.5小时：在已有开发轨迹上运行CoDE，逐检查点对照DEER，观察停止原因和最终回答。
- 1小时：整理当前 `use_log`、只累积下降段、阈值比较、分隔词、ramping steps及极短试答问题。区分运行修补、数值策略、论文算法差异。
- 0.5小时：明确本轮要冻结的实现口径。上游复现与论文公式版本分别命名、隔离结果，不能混合。

**产物：** 一条可解释的CoDE记录；公式/配置差异清单；本轮方法版本决定。

**通过条件：** 能解释一次实际的停止或未停止过程；关键差异均有记录和处理决定。关键数值问题未处理时，不进入批量运行。

### D6：小规模运行诊断、长序列与恢复检查

**位置：服务器运行，Mac审核。目标：证明可以稳定执行并估算资源。**

- 1小时：固定10–20条独立开发轨迹及样本ID，运行三方法。此批用于诊断，不用测试集准确率挑参数。
- 2小时：检查短、中、长轨迹；加入接近目标上下文长度的资源压力检查，核验包括前缀、试答和最终补答在内的显存/内存需求。合成压力输入只测试资源，不计效果。
- 1小时：在样本保存边界验证一次停止与恢复，检查唯一记录数、漏题、重复和版本匹配；避免故意打断未保存的长生成。
- 1小时：分别统计模型加载、基础生成、forceans、DEER探测、CoDE探测、判分的耗时和峰值显存。
- 1小时：据实测重算正式任务的时间、预算和后续排期，加入长尾及失败余量。

**产物：** 运行诊断小结、恢复检查、耗时/显存记录、更新后的预算与时间范围。

**通过条件：** 输出完整性可靠；目标长上下文资源通过或已选定可行硬件；能区分纸面token指标与实际开机成本。仅短题跑通不算通过32K资源检查。

### D10：统计、误差分析和复现报告

**位置：Mac为主。目标：得到一份自己能解释、别人能核验的复现结果。**

- 1小时：核对唯一键、文件数量、配置及判分完成情况，然后再使用汇总程序。`compact.py` 并非必需且不会去重，第一期可跳过。

- 1小时：按题做配对统计；同一道题的两次rollout作为一组，避免当成两道独立题。报告不确定性，不仅报告小数点后的差异。
- 1小时：查看预先选定的正确→错误、错误→正确、停止/未停止案例及判分分歧，分析现象，不据此回调测试参数。
- 1小时：完成复现报告、可重复命令、配置与版本清单；同步必要代码和整理后的结果。原始输出备份在约定存储，权重/密钥/大批原题不进Git。
- 0.5小时：用自己的话讲述整个流程，并列出已解释的问题和仍未知的问题。

**产物：** `results/` 中的复现报告、汇总表/图，必要的代码与配置，以及原始结果的备份索引。上述产物在实际完成后生成，目前不是已存在文件。

**通过条件：** 可以从保存记录重算报告；结果与论文不一致之处均标明；下一次重跑有明确入口。后续扩模型、重做校准或提出新方法另开阶段，不挤入本期验收。

## 五、数据、版本和结果的基本规则

1. 教学样例可手工构造，明确标注。开发数据用于排错；若调参另设校准数据；MATH500最终测试只用于冻结后的评估。按题划分，不能把同题不同rollout分到开发与测试两边。
2. 原始 `upstream/CoDE-Stop` 固定在 `b5081e7c2abe23bb1d19649421cc13522fee7c50`。自有代码和补丁放 `src/`、`scripts/`，配置放 `configs/`，偏差写明。不假定这些脚本现已实现。
3. 每个实验目录保存来源版本、配置、样本ID、种子、日志和状态。更换模型/代码/精度/生成设置后不能只凭同名文件继续复用缓存。
4. 输出token、试答开销、论文Cost、实测墙钟时间分别记录。当前实现先生成基础轨迹再探测，不能以回放结果直接声称在线加速。
5. 公开参数重跑与AMC23重新校准是不同任务。若没有复现AMC流程，在报告中明确说明。
6. 数据与结果异常先查清。正式测试结果可以帮助定位实现错误，但若据此设计新规则，应记录测试集已参与开发，并安排新的确认评估。

## 六、顺延与调整规则

- **按证据推进。** 每个D阶段分为未开始、进行中、受阻、待核验、完成。运行结束只证明程序退出；完成需满足该日验收标准。
- **未完成不清零。** 保存已完成部分，下一次先做剩余任务；已经核验的下载、环境和结果不重做。
- **不叠加两天任务。** 前日剩余工作成为次日优先项，后续依赖阶段整体后移；每天仍以6小时核心任务、最多8小时为基准。
- **分开处理阻塞。** 下载/服务器问题时可并行读代码、手算、整理配置；数值或结果完整性问题未解决时不扩大实验。每天最多安排三个主目标。
- **连续两次被同一问题卡住。** 助手重新检查根因和路线，给出最小解决方案，例如调整依赖组合或硬件、分离判分重试；不要求反复执行同一失败命令。
- **进度快时允许合并。** 已有证据满足两个阶段的验收就合并推进；保留必要的长序列、数值和数据完整性核验。
- **根据实测调整。** D6以后用实际耗时重排计算窗口。如果预算不足，明确保存已完成的缩减结果并调整范围，不能将小样本称为完整MATH500复现。
- **不把备用日当固定作业。** 2–4天缓冲用于真实遇到的困难，用不完可提前结束；出现重大兼容或吞吐问题时仍可能超过这一窗口。

每天收到汇报后，由指定主对话更新当前进度主记录（接入前为Markdown，接入验收后为Notion），回复：已核验完成项、当前阻塞、下一天最多三个主目标、时间分配、后续顺延影响。只有用户汇报或明确安排了检查时才更新，不假设后台已自动看到进度。辅助账号给出建议，由主对话统一合并。
